# Alify UI audit — 7 Nov 2026

## What was audited

A source-level audit of the 39 HTML pages in `frontend-source/`, the local CSS and JavaScript, and WordPress form/settings registration. This is **not** a screenshot/pixel-coordinate sign-off: this workspace has no browser binary, and no live WordPress instance or user-provided screenshots are available. Pixel positions, actual rendered breakpoints, WordPress admin menu output, and plugin/theme interactions therefore cannot be independently observed here.

## Confirmed findings

### P1 — Form and Form Template editing is incomplete without ACF Pro

**Affected screens:** Dashboard → Forms → Add/Edit Form; Dashboard → Forms → Form Templates → Add/Edit Template.

The theme registers the post types regardless of ACF, but the usable field builder, template selector, recipient/success fields, and form settings are registered only behind ACF callbacks. `inc/acf.php` returns early when ACF functions are unavailable, and local field groups are registered on `acf/init`. The README calls ACF Pro optional for activation, which can make these screens appear broken or empty if the plugin is not active. The theme does not currently provide a native fallback form editor or a clear admin notice explaining this dependency.

**Impact:** an Administrator may see the post-type screen but have no controls to define fields or reusable templates. This is a real conditional UI gap; it is not a pixel defect and does not depend on viewport size.

**Evidence:** `inc/acf.php` (ACF availability guard and form field groups); `README.md` (ACF Pro optional statement).
